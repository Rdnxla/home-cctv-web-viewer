# Phase 3: Biome and Style Audit

Precondition: Phase 1 is `done`. Direct modifications to code and configurations are strictly forbidden: run `check`/`lint`/`format` ONLY, without `--write`/`--fix` flags.

## Steps

1. **Config Analysis**: Inspect `biome.json(c)` and verify the Biome version via `package.json` or `$schema`. Document the following settings: formatter (indentation, line width, quotes, semicolons), linter (enabled groups, disabled or modified rules with their severity levels), organizeImports/assist, `files.ignore/includes`, and `overrides` (for tests, mocks, and configs). Check whether the `recommended` ruleset has been disabled.
2. **Execution**: Run `<pm> exec biome check .` to collect all diagnostics without any limits on the output count by using the `--max-diagnostics=none` flag. If the project fails validation, this is expected behavior—do not attempt to fix it.
3. **Result Aggregation**: Group the output data by rule (with total counts), by layer and slice (identifying hot spots), and by type (lint / format / imports). Highlight the top 10 breaking rules. Separate issues into those that are auto-fixable and those requiring human intervention. Save the exact command and its raw output to `reports/generated/biome-check.txt` (if the output is excessively large, truncate it and state the number of lines omitted).
4. **Configuration Drift**: Identify rules that are currently disabled but fully respected by the codebase (which can be safely enabled), as well as rules that are disabled because the code violates them at scale (technical debt). Base your conclusions strictly on hard data, not assumptions.
5. **Implicit Conventions**: Analyze unwritten conventions that Biome does not enforce. For each convention, calculate its frequency using `rg` and specify its adoption rate. This includes: file naming patterns (PascalCase/kebab/camel) by file type; named vs. default exports; naming styles for hooks and test files; component syntax styles (function vs. arrow functions, prop typing methods); location of type definitions; import formatting (path aliases vs. relative paths, explicit `import type`); and naming conventions for Query keys and hooks. Define a convention as any pattern adopted by ≥80% of the codebase; otherwise, mark it as "no unified style."
6. **Architectural Boundary Enforcement**: Determine if the current Biome configuration is capable of safeguarding architectural boundaries (e.g., restricting specific imports via overrides). Verify this using the local documentation for your Biome version located in `node_modules/@biomejs/biome` without external network requests; if uncertain, mark it as `UNVERIFIED`. Suggest elements that can be automated (either via Biome or a specialized tool like Steiger for FSD) and specify any additional dependencies required for implementation.
7. **Tooling Conflicts**: Check for conflicting or redundant developer tools, including remaining ESLint/Prettier configurations, `lint-staged`, husky hooks, scripts in `package.json`, and IDE workspace settings in `.vscode/settings.json`.

## Output

1. `docs/ai/reports/03-biome-audit.md`: A concise summary with metrics | A configuration overview table detailing key settings | Structured `check` results in tabular format | Configuration drift analysis | Identified issues cataloged as `BIO-NNN` | Recommendations on rules to enable or tighten along with their implementation cost | Remaining `UNVERIFIED` items.
2. `.agents/skills/fe-architecture-map/references/conventions.md`: Populate this file according to the template using the actual established conventions, including their measured adoption rate and a reference file path example for each.
3. Update `docs/ai/audit-plan.md`.
