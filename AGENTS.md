# Задача: аудит структуры проекта

## Режим работы
Ты анализируешь ТОЛЬКО структуру проекта и даёшь рекомендации по её улучшению.

## Что разрешено
- Смотреть дерево каталогов и имена файлов (`ls`, `tree`, `find` с -type/-name)
- Смотреть размеры файлов и количество файлов в папках (`du`, `wc -l` по списку файлов, `find ... | wc -l`)
- Читать конфигурационные и манифестные файлы, которые описывают проект:
  README.md, package.json, pyproject.toml, requirements.txt, Cargo.toml,
  go.mod, Dockerfile, docker-compose.yml, .gitignore, Makefile, tsconfig.json

## Что ЗАПРЕЩЕНО
- Открывать, читать, выводить (`cat`, `head`, `tail`, `less`, `grep`, `sed`, `rg` по содержимому)
  файлы с исходным кодом: .py .js .ts .tsx .jsx .go .rs .java .cs .cpp .c .h .php .rb и аналогичные
- Анализировать содержимое кода любым способом, в том числе через git diff/log -p
- Изменять, создавать или удалять любые файлы в проекте
- Работать за пределами текущей рабочей папки

## Что оценить
- Логичность и единообразие именования папок и файлов
- Разделение ответственности (слои, модули, фичи)
- Глубина вложенности, «свалки» (utils, misc, common), дублирование структур
- Расположение тестов, конфигов, документации, скриптов, ассетов
- Мусор в репозитории: артефакты сборки, .env, кеши, большие бинарники
- Соответствие общепринятым конвенциям для обнаруженного стека

## Формат ответа
1. Краткое описание того, что за проект и какой стек (выводы по структуре и манифестам)
2. Найденные проблемы, по убыванию важности
3. Конкретные рекомендации: что куда переместить / переименовать / добавить
4. Предлагаемое целевое дерево каталогов
5. Если для вывода нужно смотреть код, скажи об этом, но код не читай
